# Design Doc

Design Doc の目的は、実装前に不確実性を可視化し、手戻りを減らせる範囲で解消することである。完璧な予測や固定テンプレートを求めず、変更の規模、寿命、可逆性、リスクに応じて詳しさを調整する。

## 調査と根拠

既存の文書規約、実装、設定、運用契約を先に確認する。現在の挙動と制約を事実として記述し、設計判断、推測、未検証事項と区別する。確認できない情報を自然な仮定で埋めず、意思決定に影響するものは懸念点または未決定事項として扱う。

読者が判断を再現できるだけの背景、目的、対象範囲、対象外、要件、制約を示す。必要に応じて、構成、データ、API、障害時の挙動、セキュリティ、可観測性、移行、ロールバック、検証方法を説明する。関係しない定型セクションは追加しない。

## 意思決定の記述

提案を結論だけで終わらせず、次の3項目を明示する。独立した節にするか、既存フォーマットへ統合するかは文書に合わせる。

### 代替案

実際に採用可能な選択肢と比較基準を示す。各案について、満たす要件、利点、コスト、失う性質、却下理由を判断に必要な粒度で書く。現状維持が現実的なら、それも候補に含める。数を増やすためだけの案や、最初から成立しない案を水増ししない。

選択した案がどのトレードオフを受け入れた結果なのかを明記する。負荷、データ量、利用者数、変更頻度、保守期間などが判断を左右する場合は、想定する時間軸と規模を数値または検証可能な条件で示す。

### 懸念点

案を選んだ後にも残るリスクと、作成者だけでは解消できずレビューで助けが必要な未知を記す。代替案の却下理由とは分ける。

各懸念には、成立条件、想定される影響、検知方法、緩和策、解消に必要な証拠を可能な範囲で対応づける。影響が無視できないのに検証できていない事項は、滑らかに断定せず未検証と示す。

### 未決定事項

今は決めない事項について、少なくとも次を示す。

- 何を決める必要があるか
- なぜ今は決めないのか
- いつ、誰またはどの役割が決めるのか
- 判断に必要な情報や先行条件
- 未決定のまま実装へ進めるか、開始を止めるブロッカーか

「後で決める」だけで終わらせない。実装時に決める事項は、承認後に追跡可能なタスクへ変換できる形にする。

## 完了条件

文書の最後に、決定済み事項、受容した残存リスク、未決定事項、実装開始を妨げるブロッカーを読み分けられる状態にする。レビューで求める判断や専門知識がある場合は明示する。

情報不足でも有用な草案を作れるなら、仮定と未知を明示して進める。選択によって設計が大きく変わる情報だけを質問する。

既存の Design Doc をレビューするときは、提案の好みだけで評価せず、代替案の妥当性、懸念の深さ、未決定事項の扱い、根拠と結論の対応を点検する。更新時は過去の判断理由を消さず、何が新しい証拠によって変わったかを残す。
