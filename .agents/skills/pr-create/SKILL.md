# pr-create — PR作成フロースキル

## 全体フロー

1. 差分を把握し、PRに分割すべきか判断する
2. 会話ログを振り返り、コメントが必要な箇所を特定する
3. ブランチを用意する（必要なら作成）
4. 必要なコメントをコードに追記する
5. コミットを意味単位に分割して積む
6. pushする
7. PR説明文を三点で構成して`gh pr create`で作成する
8. 複数PRがある場合は順番に繰り返す

---

## Step 1: 差分把握とPR分割判断

```bash
git status
git diff HEAD
git log main..HEAD --oneline  # mainとの差分コミット一覧
```

差分を把握したら、**PRを何本に分けるかを先に決める**。

PR分割の基準：
- **目的が違う** → 別PR（機能追加とバグ修正を混ぜない）
- **レビュアーが変わりそう** → 別PR（設定変更とロジック変更など）
- **独立してマージ・revert できるか** → できない組み合わせは同じPRに留める
- **「〜と〜を変えた」とPRタイトルを書きたくなる** → それは複数PRのサイン

複数PRに分割する場合は、それぞれ別ブランチを作って順に作業する。依存関係がある場合は、依存される側のPRを先に出す。

---

## Step 2: コメント追記

PRを出す前に、**会話ログを読み返して**以下に該当する箇所がないか確認する。該当があればコードにコメントを追記してからコミットに含める。

コメントが必要なサイン：
- **議論して決めた設計判断** — 複数の選択肢を検討して一方を選んだ経緯（「なぜこっちにしたか」が消えると同じ議論が再発する）
- **バグ修正で明らかになった非自明な制約** — 「こう書くと壊れる」という知識がコードから読み取れない場合
- **一見おかしく見えるが意図的なコード** — 将来の自分や別の開発者が「なぜこう書いてあるんだ？」と直したくなりそうな箇所

コメントに書くべき内容：
- **WHY**（なぜこう書いたか）であって WHAT（何をしているか）ではない
- 「〇〇の場合に壊れるため」「〇〇と議論して〇〇を選んだ」など具体的な理由
- 一行で収まらない場合は複数行可

コメントが不要なケース：
- コード自体が自明で、読めばわかるもの
- 議論なく自然に決まったもの
- 一時的な実装で後で消えるもの（その場合は `TODO:` で十分）

---

## Step 3: ブランチ名

- **英語のみ**、kebab-case（例: `add-user-auth`, `fix-login-redirect`）
- 個人名・ユーザー名・メールアドレスは**絶対に含めない**
- 変更内容が一目でわかる動詞＋名詞の形を基本とする（`add-`, `fix-`, `update-`, `remove-`, `refactor-`）
- 既にmain以外のブランチにいる場合はそのまま使う

```bash
git checkout -b <branch-name>
# すでに適切なブランチにいる場合はスキップ
```

---

## Step 4: コミット

コミットメッセージの指針：
- **Conventional Commits** に従う：`<type>(<scope>): <description>`
- `<description>` は lowercase、末尾ピリオドなし、imperative mood
- `<scope>` は**原則付ける**。変更対象のコンポーネント・ディレクトリ・ツール名など（例: `feat(auth): add JWT support`、`chore(aqua): update packages`）
- 本当にスコープが一つに絞れない横断的変更のみ省略可
- 使える型：

| 型 | 用途 |
|---|---|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | コードの意味に影響しない変更（空白・フォーマット等） |
| `refactor` | バグ修正でも機能追加でもないコード変更 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` | ビルドシステム・外部依存の変更 |
| `ci` | CI設定・スクリプトの変更 |
| `chore` | ソース・テスト以外の雑務（aqua update等） |
| `revert` | 過去のコミットの取り消し |

### コミット分割の原則

変更が複数ファイル・複数目的にまたがる場合、**必ず意味単位に分割してコミットを積む**。一括コミットはしない。

分割の判断基準：
- **type が変わる** → 別コミット（`fix` と `feat` を混ぜない）
- **scope が変わる** → 基本的に別コミット（`auth` と `ui` の変更を混ぜない）
- **独立して revert できるか** → できない粒度なら分割を検討する
- **「〜と〜を変えた」と説明が必要になる** → それは複数コミットのサイン

分割の手順：
1. `git diff` で全変更を把握し、意味のまとまりをリストアップする
2. まとまりごとに `git add <files>` でステージングしてコミット
3. 依存関係がある場合は依存される側から先にコミットする

```bash
# 例: 設定追加 + バグ修正 + ドキュメント更新が混在している場合
git add config/foo.yaml
git commit -m "feat(config): add foo configuration"

git add src/bar.go
git commit -m "fix(bar): handle nil pointer on startup"

git add docs/setup.md
git commit -m "docs(setup): update foo configuration guide"
```

- `git add -A` / `git add .` は使わない。必ずファイル単位で確認してステージする

git push -u origin <branch-name>

## Step 6: PR作成

### PRテンプレートの確認

まずリポジトリにPRテンプレートがないか確認する：

```bash
ls .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE.md 2>/dev/null
ls .github/PULL_REQUEST_TEMPLATE/ 2>/dev/null
```

- **テンプレートがある場合** — その構造を必ず尊重する。セクション見出し・項目をそのまま使い、中身だけを三点の観点で埋める
- **テンプレートがない場合** — 下記のデフォルト構成を使う

### PR説明文の三点構成（テンプレートなしの場合）

差分・コミット・コード全体から以下を推測して書く：

1. **変更の目的** — なぜこの変更が必要だったか（背景・課題・動機）
2. **実現方法の骨子** — 何をどう変えたか（アプローチの核心、主要ファイル）
3. **影響範囲と検証方法** — 何に影響し、何で確認できるか（手動確認・テスト・ビルドなど）

書き方の注意：
- 箇条書きより短い散文を優先する。読み手が「なるほど」と思えるレベルの情報密度を目指す
- コードの羅列ではなく、**意図と判断**を説明する
- 影響範囲が不明な場合は「影響なし / 単体で完結」と正直に書く

### PRタイトル

コミットメッセージと同じ規則で、変更全体を一行で表す。

### gh コマンド

通常（デフォルト）:
```bash
gh pr create --title "<title>" --body "$(cat <<'EOF'
## 変更の目的

<why>

## 実現方法の骨子

<how>

## 影響範囲と検証方法

<impact-and-verification>
EOF
)"
```

ユーザーが「draft で」「ドラフトで」と指定した場合のみ `--draft` を追加:
```bash
gh pr create --draft --title "<title>" --body "..."
```

---

## 判断の優先順位

- ユーザーがブランチ名・コミットメッセージ・PR内容を指定した場合はそれを尊重する
- 曖昧な場合は推測して進めてよい（確認質問で止まらない）
- 「なぜ」が差分から読み取れない場合でも、コードの変化から合理的に推測して書く
